## critical

### 1. SQL-инъекция — `BookingController.php:23-26`
`room_id`, `starts_at`, `ends_at` из запроса подставляются в SQL строкой. Например, `room_id = "1 OR 1=1"` или `ends_at = "x' OR '1'='1"` меняют запрос; данные можно читать и портить (stacked queries зависят от драйвера, но подзапросы работают всегда).
**Исправление:** сначала валидация (`exists:rooms,id`, `date`), затем запрос через Eloquent или с bindings: `Booking::where('room_id', $room->id)->where('starts_at', '<', $end)->where('ends_at', '>', $start)->exists()`.

### 2. Нет проверки автора при отмене — `BookingController.php:47`
`Booking::findOrFail($id)->delete()` удаляет любую бронь любому аутентифицированному пользователю. Нарушает правило «отменить может только автор».
**Исправление:** `abort_unless($booking->user_id === $request->user()->id, 403)` (или Policy). Отсутствующая бронь по-прежнему 404.

### 3. Автор задаётся клиентом — `BookingController.php:37`, `Booking.php:11`
`Booking::create($request->all())`, а `user_id` есть в `#[Fillable]`. Борис может создать бронь «от имени» Анны (пример в README сам отправляет `user_id`): бронь появится у Анны, а автор-подделка обходит правило «отменить может только автор». Также можно передать любые другие fillable-поля.
**Исправление:** брать только валидированные данные, `user_id` — из `$request->user()->id`.

## major

### 4. Впритык = конфликт — `BookingController.php:25-26`
Условие `starts_at <= new_end AND ends_at >= new_start` включает границы: 10:00–11:00 и 11:00–12:00 считаются пересекающимися. Нужны строгие неравенства: `starts_at < new_end AND ends_at > new_start`.

### 5. Рабочее время — `BookingController.php:32-35`
- `Carbon::parse` сохраняет смещение клиента, поэтому `$start->hour` — это час **в поясе клиента**, а не офиса. Бронь в 10:00+03:00 для новосибирской комнаты (14:00 по Новосибирску) проходит, а 09:30+07:00 из-за смещения может не пройти.
- Проверяется только начало: бронь 19:00–23:00 или через полночь проходит.
- Нет проверки, что конец позже начала.
**Исправление:** перевести оба момента в `$room->office->timezone` (`->setTimezone(...)`), проверить `start >= 09:00`, `end <= 20:00`, одну локальную дату, `end > start`.

### 6. Потеря смещения при сохранении — `BookingController.php:32,37`
Колонки `timestamp` в PostgreSQL — `timestamp without time zone`. Eloquent приводит строку `2026-11-02T10:00:00+03:00` к Carbon (смещение сохраняется) и форматирует как `Y-m-d H:i:s` без перевода в таймзону приложения (UTC), поэтому в БД ляжет `10:00:00`, а не `07:00:00`. Сырой запрос из `store` сравнивает литерал с отброшенным смещением. Итог: пересечения и «сегодня» считаются неправильно для любых запросов не в UTC. **Воспроизведено:** `starts_at: 2026-11-02T10:00:00+03:00` сохранился как `2026-11-02 10:00:00` (должно быть `07:00:00`), а в ответе API вернулся как `10:00:00Z`.
**Исправление:** перед сохранением явно приводить к UTC (`->utc()`), и/или перейти на `timestampTz`.

### 7. Нет валидации — `BookingController.php:21-37`
Нет `validate()`: нет `room_id`/`title`/дат → 500 от БД или от `Carbon::parse`; несуществующая комната → нарушение FK → 500; длительность не проверяется (0 минут, 10 часов, шаг 15 минут); `ends_at < starts_at` допустим. Проверка конфликта идёт до проверки времени, а ошибки в разных форматах (`error` вместо стандартного 422 с `errors`).
**Исправление:** `StoreBookingRequest` с правилами формата и одной проверкой бизнес-правил; ответы 422 в стандартном формате Laravel.

### 8. Гонка — `BookingController.php:23-37`, `…000003_create_bookings_table.php:11-19`
Проверка и вставка не атомарны: два параллельных запроса оба увидят свободный слот и оба вставят. На уровне БД ничего не защищает (ни exclusion constraint, ни уникальности).
**Исправление:** `DB::transaction` + `Room::lockForUpdate()` вокруг проверки и вставки; дополнительно — exclusion constraint на PostgreSQL (`btree_gist`, `tsrange(starts_at, ends_at, '[)')`), если расширение доступно.

### 9. `today` и часовой пояс — `BookingController.php:55`
`whereDate('starts_at', today())` сравнивает с «сегодня» в UTC (`config/app.php:68`). Для Новосибирска (UTC+7) с 00:00 до 07:00 местного времени «сегодня» ещё вчерашнее; для Москвы — с 00:00 до 03:00. Исправлять не требуется (по заданию), но это баг.
**Исправление:** границы дня считать в `$room->office->timezone` и переводить в UTC; запрос по диапазону `starts_at >= start AND starts_at < end` (заодно использует индекс, в отличие от `whereDate`).

## minor

### 10. Ответ создания — `BookingController.php:42`
Возвращается сырая модель со статусом 200. Лучше 201 и единообразный JSON (Resource).

### 11. Мелочи в `today` — `BookingController.php:57-60`
`$b->user->name` в цикле — N+1 (`->with('user')`); нет `orderBy('starts_at')`; `$b->starts_at . ' – ' . $b->ends_at` отдаёт время в UTC без указания пояса — клиент не поймёт, что это не локальное время офиса.

### 12. `Log::withContext` — `BookingController.php:39-40`
Контекст задаётся после создания записи и уже после того, как канал мог быть создан; он общий для всех последующих логов процесса (в долгоживущем воркере утекает между запросами). Проще: `Log::channel('bookings')->info('Booking created', ['booking_id' => $booking->id])`. Насколько `withContext` влияет на канал `bookings` — **не проверял**.

### 13. Индексы и ограничения — `…000003_create_bookings_table.php:15-16`
Нет индекса `(room_id, starts_at)` для проверки пересечений и `today`; нет `CHECK (ends_at > starts_at)`; нет защиты от пересечений на уровне БД (см. №8).

### 14. Роуты — `routes/api.php:6-11`
- Нет `throttle` на `POST /bookings` — можно массово создавать брони.
- `{id}` в `destroy` без route model binding — работает через `findOrFail`, но привязка `Booking $booking` + Policy была бы чище.

### 15. Тесты — `tests/Feature/BookingIndexTest.php`, `BookingFactory.php:17`
Покрыт только `index`; для `store`, `destroy`, `today` тестов нет, поэтому все выше найденные баги не ловились. Фабрика ставит `now()->addDay()->setTime(10, 0)` в UTC, а не по времени офиса; в тестах правил времена нужно задавать явно.

### 16. `offices.timezone` — `…000001_create_offices_table.php:14`
Произвольная строка без валидации; невалидное имя пояса сломает `setTimezone` в рантайме. Сейчас данные только из сидера, поэтому риск низкий; при росте — enum/валидация при создании офиса.

### 17. 500 вместо 401 без `Accept` — `bootstrap/app.php`
**Воспроизведено:** `curl localhost:8000/api/bookings` без токена и без `Accept` → 500, в логе `Route [login] not defined` (`UrlGenerator.php:542`). Утверждение README верно: `shouldRenderJsonWhen` не помогает, потому что редирект на несуществующий роут `login` строится раньше. Исправление: `$middleware->redirectGuestsTo(fn () => null)` (или JSON-401 для `api/*`).

## Выглядит подозрительно, но проблемой не является

- **`orderByRaw('starts_at DESC')`** — `BookingController.php:17`. Строка статическая, пользовательский ввод не подставляется, инъекции нет. Лучше `orderByDesc('starts_at')` ради читаемости.
- **`index` отдаёт только брони пользователя** — `where('user_id', $request->user()->id)`: фильтр по аутентифицированному пользователю, чужие брони не видны. Пагинация по 20 — разумна.
- **`Booking::findOrFail($id)`** в `destroy` — несуществующий id честно даёт 404. Проблема только в отсутствии проверки автора (№2).
- **Внешние ключи** `room_id`, `user_id` с `constrained()` — правильно; без валидации они превращаются в 500 (№7), но сами по себе корректны.
- **`Room $room` в `today`** — route model binding даёт 404 для несуществующей комнаты.
- **`auth:sanctum` на всей группе** — аутентификация настроена правильно; для запроса с токеном всё работает.
